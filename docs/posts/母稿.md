## 正文

### 一、先说我的环境

家里是一台 NAS（飞牛 OS，AMD 平台，64GB 内存），上面常年跑着 20 多个容器：Jellyfin、Emby、Plex 三套媒体库，qBittorrent、MoviePilot、alist、Home Assistant、mihomo、searxng、还有一堆临时起的新容器。

一开始用的是 Portainer，确实够用。但用了大概半年之后，遇到了几个让我实在忍受不了的问题：

**第一，Compose 项目是分裂的。** Portainer 的 Stack 是它自己的一套数据库存着的，跟我硬盘上 `/vol1/1000/docker/` 里的 compose 文件完全是两回事。我加了个容器之后，compose 文件并没有跟着变，下次 `docker compose up -d` 就把它覆盖回去了。反复踩坑之后我每次改 compose 都得去 SSH 里手动改文件，再回来点一下「重新部署」。

**第二，文件管理基本等于没有。** 想看个 compose 文件内容，只能 SSH 进去 `cat`。想传个配置文件进去，得开 SFTP 客户端。

**第三，远程节点是 Pro 功能。** 我还有一台小机器跑 Docker，Portainer CE 里管理远程节点要在网页里一个个敲 SSH 私钥、端口、密码，非常痛苦。

**第四，也是最让我难受的：界面全是英文。** 我不是英语母语，查个参数经常要开翻译软件。

于是我决定自己写一个。用了两个周末，写了个叫 **Docker-Link** 的面板，部署在自己 NAS 上用，到现在跑了两个多月。

### 二、它能干什么

**容器 / 镜像 / 卷 / 网络 / 端口的完整管理**，增删改查、日志、终端、重启，这些是基本盘。

**Compose 项目管理**是我最满意的部分：它直接扫描我硬盘上真实的 compose 目录，把每个项目当成一个「项目」列出来，点进去可以看有哪些服务、哪些容器在跑、哪个挂了。编辑完 compose 文件点「部署」，走的是 `docker compose up -d`，不是我另造一套逻辑。所以**硬盘上的文件永远是唯一事实来源**，不会出现 Portainer 那种「界面改了但文件没改」的割裂。

**文件管理器**可以浏览、在线编辑、上传、下载。我现在的习惯是：所有 compose 文件都放一个目录，在面板里直接编辑，不再开 SSH。

**Web 终端**是我用得最多的功能。点一下容器就进去，是个真正的交互式 shell（走的是 `docker exec` + PTY，不是那种只能看不能输的伪终端）。排查问题的时候省掉了一大半 SSH 操作。

**多节点管理**支持两种方式：一种是装一个 Agent 模式（HTTP + Token 认证），一种是纯 SSH 通道。我的小机器用的是 SSH 方式，不需要额外装东西。

**容器更新**这块我做了个兜底逻辑。众所周知国内拉镜像慢，所以我做了三层：先走加速源，不行直连 dockerd，再不行就在容器内走代理 `docker load`。判断「有没有新版本」不是看 tag，而是**比对镜像 digest**，这个细节很关键——很多面板 tag 没变但底层镜像已经更新了，它就再也不提示更新。

**还有企业微信告警**，容器挂了、更新完成，可以直接推到企业微信群。我把家里几个关键服务都接上了。

**图标管理**会自动给容器匹配图标，没匹配上可以自己上传。

### 三、怎么部署

三行命令的事：

```bash
docker run -d --name docker-link --restart always -p 9080:9080 \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  -v /opt/compose:/opt/compose:rw \
  -v docker-link-data:/data \
  -v docker-link-config:/app/config \
  -e TZ=Asia/Shanghai \
  lichangzhou/docker-link:latest
```

打开 `http://你的NAS地址:9080` 就能用了。

### 四、说说缺点

既然是自用工具做的，我觉得有必要把不行的也讲清楚：

- **目前只发布了 amd64 架构的镜像**。ARM 机器（部分国产 NAS、树莓派）用不了，得自己构建。这是我没做好的地方。
- **默认没有内置认证**。它挂载了 `docker.sock`，能操作 Docker 基本就等于有宿主机 root 权限，所以我自己的做法是设了 `ADMIN_USER` / `ADMIN_PASSWORD`，并且只在局域网内访问，**千万别直接暴露到公网**。
- 界面是单文件的（一个 `index.html` 打包到底），好处是零构建、镜像小，坏处是功能一多代码就有点难维护。
- 项目还很年轻，还在快速迭代，接口可能会变。

### 六、这套栈里另外两个项目

Docker-Link 负责把容器跑起来，但一个能用的家庭媒体栈不止运维这一环。我这套环境一共三个项目，都是我自己写的：

Docker-Link 负责把容器跑起来，**EvoLink** 负责把媒体库理清楚（缺口比对 / 归档刮削 / 权重洗板 / 302 换链），**Playable** 负责在 Android / Windows / iOS 上把 `.strm` 库看下去。三个仓库都在我 GitHub 账号下：https://github.com/lichangzhou

分开用也完全可以，但串起来才是一条完整链路——EvoLink 生成的 `.strm` 里写的是签名直链、用 HTTP 302 跳转到真实地址，所以链接是有时效的；播放端必须跟随 302，不能把 `.strm` 里的 URL 当最终地址缓存下来。Playable 就是按这个前提实现的。

如果你是自建家用，那这套东西应该挺合身的；如果是生产环境，**务必自己评估安全模型**，别直接照抄我的配置。
